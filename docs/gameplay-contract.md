# 카멜론 게임성 계약서

상태: Phase 7 모바일 가로 입력·레이아웃 보강 완료 · 온라인 방 개편은 [online-rooms-plan.md](online-rooms-plan.md)에서 별도 페이즈로 진행

이 문서는 기능 목록이 아니라, 다음 리빌드에서 게임성·맵·AI·네트워크가 같은 기준으로 움직이게 하기 위한 계약서다. 원작의 핵심 재미는 참고하되 원작의 코드·리소스·미확인 규칙을 복제하지 않는다.

## 1. 제품 목표

카멜론은 최대 8인이 짧은 라운드를 반복하는 실시간 숨바꼭질 게임이다.

- 카멜레온은 배경을 관찰하고, 색·패턴·자세를 조정하고, 술래의 판단을 속인다.
- 술래는 이동·시야·소리·색 차이·실루엣을 조합해 의심 대상을 좁힌다.
- 한 라운드 안에 이동 위험, 위장 준비, 정지 판단, 발견 긴장감이 모두 존재해야 한다.
- 온라인은 채널 1개 아래 여러 방을 두고, 방마다 2~8인이다. 방 목록은 Redis TTL 캐시, 게임 상태는 Playroom 세션에만 있다 ([online-rooms-plan.md](online-rooms-plan.md)).
- 감염 모드·AI 고정 역할·탄약 제한은 기본 모드가 아닌 선택 모드다.

## 2. 재미 검증 질문

각 라운드가 아래 질문에 “예”라고 답할 수 있어야 한다.

1. 카멜레온이 숨을 장소를 고르는 과정에 위험과 선택이 있는가?
2. 단색으로 칠하는 것보다 위치·자세·실루엣을 맞추는 것이 유리한가?
3. 술래가 발견 직전에 얻는 시각·소리 단서가 이해 가능한가?
4. 술래가 틀리게 판단하거나 총을 낭비할 위험이 있는가?
5. 라운드가 끝난 뒤 “저기에 숨어 있었구나”라는 회고가 생기는가?
6. AI도 순간이동이나 고정값이 아니라 같은 규칙으로 플레이하는가?

## 3. 기본 라운드 계약

```text
lobby -> prepare -> hide -> hunt -> reveal -> result -> lobby
```

- `lobby`: 참가·준비·맵·규칙 설정
- `prepare`: 전원이 맵의 집합 지점(`gather`) 링으로 순간이동해 정지하고, 방 시계에서 파생되는 이름 룰렛이 감속하며 술래에서 멈춘다(모든 클라이언트 동일 프레임). 끝나면 카멜레온은 스폰으로, 술래는 술래 스폰으로 이동
- `hide`: 카멜레온이 직접 이동해 표면을 샘플링하고 칠함
- `hunt`: 술래가 이동·관찰·추리·태그 수행
- `reveal`: 모든 위치와 위장 결과 공개
- `result`: 승패·개인 성과·다음 라운드 준비

최소 2인이 모이지 않은 라운드는 시작하지 않는다. 8인 라운드의 기본 역할은 1 술래와 7 카멜레온으로 시작하고, 실제 플레이테스트 결과에 따라 2 술래 옵션을 별도로 조정한다.

## 4. 맵 계약

초기 8인 맵의 목표값은 고정 법칙이 아니라 플레이테스트용 KPI다.

- 3개 핵심 구역
- 2개 이상의 순환 루트
- 중앙의 빠르지만 위험한 경로와 외곽의 느리지만 안전한 경로
- 주요 은신처 8~12개
- 보조 장애물 16~24개
- 20~30%의 열린 이동 공간
- 모든 스폰에서 직접 보이는 주요 은신처 금지
- 2명이 동시에 통과할 수 없는 불필요한 병목 금지
- 가장 먼 구역 접근 6~10초
- 전체 순환 이동 25~35초

2026-09-19 재개편 이후 맵은 `rooms`(방 선언)로 작성한다. 실내 맵은 벽이 천장까지 닿고 방마다 천장 판과 조명 기구가 있으며, 야외 맵은 하늘 돔·태양·지평선과 낮은 울타리 경계를 가진다. 방의 `light`(0~1)가 술래 가시성 계수(0.85~1.15)와 AI 은신 선호에 반영된다. 감사 지표: 시야 개방도(실내 ≤45%, 야외 ≤60%), 방 수 ≥3, 명암 대비 ≥0.4, 면적 대비 은신처, 소품 겹침, 벽-천장 밀착.

맵 오브젝트는 단순한 박스가 아니라 다음 정보를 가져야 한다.

```text
propId
visualModel
collisionShape
paintableSurfaces
silhouetteProfile
coverHeight
coverQuality
navigationCost
spawnAllowed
hideAllowed
```

## 5. 시스템 경계

- `round`: 페이즈·역할·승패만 처리
- `commands`: 이동·페인트·문·발사·도발을 검증 가능한 명령으로 처리
- `simulation`: 권위 있는 상태 변화와 시간 진행
- `world`: Three.js 렌더링·충돌·카메라
- `ai`: 네비게이션·인지·행동 선택
- `maps`: 시각 모델과 충돌·은신·네비게이션 데이터를 함께 제공
- `session`: 온라인 전송과 재접속만 담당
- `rooms`: 방 코드·디렉터리(목록/heartbeat) 로직. 게임 상태는 다루지 않음
- `GameView`: 화면 조립과 입력 연결만 담당

UI에서 방 상태를 직접 통째로 덮어쓰지 않는다. 게임 상태는 명령을 통해서만 변경하며, 최종적으로 권위 있는 호스트 또는 게임 서버가 검증한다.

## 6. 출시 전 필수 검증

- 2·4·8인 역할 배정과 승패
- 재접속·퇴장·관전자 전환
- 중복 발사와 탄약 차감
- 모든 스폰의 충돌·경계·공정성
- AI의 실제 이동·탐색·은신
- MacBook 키보드·마우스
- iPhone Safari와 Android Chrome 가로 터치
- 데스크톱 60 FPS 목표, 모바일 30 FPS 하한
- 채팅 도배·금칙어·긴 텍스트 처리
- 맵별 생존 시간·발견률·이동 경로·승률

## 7. 페이즈 완료 규칙

각 페이즈는 코드가 동작하는 것만으로 완료하지 않는다.

1. 로컬 검증과 브라우저 시나리오를 실행한다.
2. 데스크톱과 모바일 입력을 확인한다.
3. 변경 파일·잔여 위험·다음 페이즈를 기록한다.
4. 커밋과 푸시 후 결과를 보고한다.

## 8. Phase 2 구현 메모

- 키보드·터치 버튼·조이스틱은 `GameInputState` 하나로 합쳐 매 프레임 동일한 이동 입력을 소비한다.
- Escape는 포인터 락을 해제하고 시야 입력을 중단한다. 창 전환·백그라운드·세로 전환에서도 입력을 비운다.
- 조이스틱 이동과 우측 시야 드래그는 포인터 캡처가 풀려도 window 이벤트로 종료·갱신된다.
- 충돌체는 회전된 사각형의 로컬 좌표에서 원형 플레이어와 검사하고, 벽 붙기 축은 렌더링된 면에 직접 스냅한다.
- 방 외곽 보정값은 렌더링 벽 두께를 기준으로 조정해 정상 이동에서 벽과 불필요하게 떨어지지 않게 한다.

## 9. Phase 3 맵 구현 메모

- 모든 맵을 8인 플레이테스트 범위인 40~42 × 30~32로 맞췄다. (이후 난이도별 크기로 변경 — §14)
- 저택·농장·하수도·백룸에 소파, 안락의자, 테이블, 책장, 의자, 화분, 스탠드, 드럼을 구역별로 배치했다.
- 각 맵은 중앙 분할 벽과 문을 기준으로 빠른 중앙 루트와 외곽 우회 루트를 함께 제공한다.
- 회전·비균일 축소된 오브젝트도 시각 크기와 충돌 프로필이 함께 축소되도록 맵 변환 단계에서 보정한다.
- 감사 기준 결과: 4개 맵 모두 주요 커버 8개 이상, 의미 있는 소품 12개 이상, 스폰 오류 0개.

## 10. Phase 4 시각 구현 메모

- 저택·농장 바닥에는 생성형 오크 텍스처, 하수도 바닥에는 생성형 산업 콘크리트 텍스처를 적용하고 맵 색으로 톤을 조정한다.
- 이미지 텍스처는 데스크톱 최대 8배, 모바일 최대 2배 비등방성 필터를 사용해 비스듬한 시점의 흐림을 줄인다.
- 맵별 포인트 조명을 추가하되 모바일에서는 광원 수와 세기를 낮춰 프레임 비용을 제한한다.
- 충돌 가능한 박스형 구조물은 작은 라운딩을 적용해 모서리와 실루엣을 완화하고, 충돌 계산 크기는 기존 맵 정의를 유지한다.

## 11. Phase 5 AI 구현 메모

- AI 카멜레온은 스폰에서 은신처까지 직접 이동하고, 중간 후보 지점을 거친 뒤 마지막 위치에서만 위장을 완료한다.
- 이동은 맵 충돌체 주변 웨이포인트 A* 경로와 슬라이드 이동을 함께 사용하며, 경로가 막히면 재탐색한다. 헌트 시작 시 목표 위치로 순간이동하지 않는다.
- 술래가 가까워지거나 시야가 열린 경우 AI 카멜레온은 다른 은신처를 점수화해 탈출하고, 이동 중에는 위장이 풀려 위험을 감수한다.
- AI 술래는 시야에 들어온 카멜레온을 추적하고, 놓치면 마지막 목격 지점을 조사한 뒤 은신처·순찰 지점을 교대로 수색한다.
- AI의 발사는 시야·조준 방향·거리·위장도·쿨다운을 모두 통과해야 하며, 클라이언트 화면만으로 즉시 발견하지 않는다.

## 12. Phase 6 온라인 상태 구현 메모

- 라운드 시작 시 `participantIds`를 고정한다. 그 뒤 입장한 플레이어는 유령 관전자이며 승패·점수·태그 대상에서 제외되고, 다음 라운드부터 참가한다.
- 호스트는 `hostId/hostName`을 방 상태에 기록한다. 승계 시 새 호스트가 이를 갱신하고 시스템 메시지를 남기며, 도발 시퀀스를 현재 값으로 초기화해 재생을 막는다.
- 강퇴는 호스트의 `kick` RPC를 대상 클라이언트가 검증(발신자 = `hostId`)한 뒤 스스로 퇴장하는 방식이다. Playroom `player.kick()`은 보조 수단이다.
- 호스트는 매 틱 현재 참가자 목록과 라운드의 술래·탈락·탄약 상태를 대조해 퇴장한 ID를 정리한다.
- 진행 중 술래가 모두 이탈하면 카멜레온 승리, 수색 중 생존자가 모두 사라지면 술래 승리로 즉시 라운드를 종료한다.
- 발사 RPC는 발신자별 단조 증가 시퀀스와 호스트 측 쿨다운을 통과해야 하며, 문 RPC는 페이즈·호출자·문과의 거리·호출 빈도를 검증한다.
- 채팅은 호스트가 메시지 길이·최근 전송 횟수·보관 개수를 제한해 도배와 상태 폭증을 막는다.

## 13. Phase 7 모바일 입력 구현 메모

- 모바일은 가로 화면만 플레이 가능하며, 세로 전환 시 포인터 락·키·터치 입력·관전 상태를 즉시 초기화하고 가로 전환 안내를 표시한다.
- 왼쪽 조이스틱은 포인터 캡처와 window fallback으로 이동 입력을 유지하고, 오른쪽 시야 패드는 패드 자체에서 드래그 델타를 소비한 뒤 캡처 불가 브라우저에서만 fallback을 사용한다.
- 조이스틱·시야·하단 액션 버튼은 `data-touch-control` 경계를 공유해 게임 캔버스의 마우스 조준·시야 입력이 터치 조작을 가로채지 않게 한다.
- 가로 화면 하단 액션은 좌우 조작 패드 사이만 사용하고 필요하면 가로 스크롤해 작은 휴대폰에서도 버튼 겹침을 피한다.
- 설치형 모바일 웹앱은 `viewport-fit=cover`와 landscape manifest 정책을 사용해 노치·홈 인디케이터 영역을 안전 여백으로 처리한다.

## 14. 이동·카메라·페인트 보강 메모

- 벽 붙기는 축 정렬된 충돌체에서만 허용한다. 회전된 소품의 대각 면에 붙으면 축 방향 이동이 몸을 면 안쪽으로 밀어 넣었다.
- 벽에서 떨어질 때(Shift·바닥에서 내려가기·C·자세 변경·감염 전환)는 모두 `exitCling → detachFromWall`로 법선 방향 0.32를 `moveWithSlide`로 이동해 다른 충돌체 안으로 들어가지 않는다.
- 벽에 붙은 채 옆·위로 이동할 때는 붙은 박스를 제외한 모든 충돌체를 `blocked`로 검사한다. 이전에는 검사가 없어 옆 벽 안으로 몸이 들어간 뒤 해제 시 반대편으로 튀어나갔다(벽 통과).
- `resolveStuck` 보정이 0.45 이상이면 얇은 벽을 관통하는 보정이므로 적용하지 않고 마지막으로 확인된 자유 위치로 되돌린다.
- 원격 플레이어 보간은 프레임 독립(`1 - e^{-16·dt}`)이며 같은 충돌체를 따라 슬라이드한다. 2.2 이상 벌어지거나 0.45초 이상 벽에 눌리면 스냅한다.
- 3인칭 카메라는 중심 + 좌우 0.22·상하 0.16 오프셋 레이 5개로 가림을 검사해 모서리·문틀에서 벽 안으로 들어가지 않는다.
- 붓은 부위별 UV 스케일(둘레·높이)로 타원 스탬프를 찍어 다리·팔에서도 몸통과 같은 실제 크기로 칠해지고, u 이음매 근처는 좌우로 한 번씩 더 찍어 틈이 없다.
- 드래그 스트로크는 폴리라인이다. 포인터가 직선을 벗어나면 이전 끝점에서 새 선분을 시작하고, 이음매를 넘는 점프(|Δu| ≥ 0.5)는 새 스트로크로 취급한다. 위장도의 칠한 범위는 선분 길이를 반영한다.
- 아레나 크기는 난이도로 정한다: 쉬움 42×32, 보통 48×36, 어려움 56×42. 모든 맵은 `rooms`(방 선언)로 최종 크기에서 직접 작성하며, 벽·문·창·천장·조명 기구는 `src/lib/maps/rooms.ts`가 생성한다. 태양 그림자 프러스텀은 맵 크기에 맞춘다.
- 커버 밀도는 면적을 따라간다. 감사가 `8 × 면적/(42×32)` 개 이상의 주요 은신처를 요구하고(`COVER_DENSITY_LOW`), 소품끼리 0.25 이상 겹치면 오류(`PROP_OVERLAP`)다. 보통·어려움 맵은 `extraCover`로 아레나 좌표에 칸막이·책상·캐비닛·소파 등을 추가하며, 기존 충돌체와 겹치거나 스폰에 붙는 후보는 자동으로 버리고 감사 스크립트가 `DROPPED`로 보고한다. 결과: 저택 14, 농장 11, 하수도 16, 백룸 26 (밀도 ≈ 1,000㎡당 10~11개로 균일).
- 문은 대기실에서도 열 수 있다(공개·결과 단계만 잠금). 점프는 현재 방의 천장(`ceilingAt`)에서 멈추고, 관전 카메라도 같은 높이를 넘지 않는다. glTF 소품은 바닥 면적에 맞춰 스케일해 보이는 크기와 충돌체가 일치한다(높이는 1.35배까지만 허용).
